# 00 · 第一性原理与心智模型：Palantir 为什么这么设计

> 本篇讲**"为什么"**——理解整套技术体系的钥匙。各子系统"怎么做"见 [01–09](./README.md)，想照着实现见 [SPEC.md](./SPEC.md)。
>
> 读法建议：先读本篇建立心智模型，再按需翻各子系统篇。**Palantir 的每一个设计，都是为消除企业数据的某一条"断裂"。**

---

## 一、Palantir 要解决的根本问题：三条断裂

企业已经有 ERP、MES、数仓、BI，为什么还需要 Palantir？因为传统栈留下了三条致命断裂：

| 断裂 | 现象 | 后果 |
|---|---|---|
| **数据 ↔ 决策 断裂** | 数据躺在仓库里，决策发生在人脑和 Excel 里 | 每次决策都要人肉捞数、拼表、凭经验 |
| **洞察 ↔ 行动 断裂** | 看到了"某物料要断供"，但改不动 ERP | 分析只能产出 PPT，落不了地 |
| **使用 ↔ 治理 断裂** | 要么锁死（安全但没人能用），要么放开（能用但不安全） | 合规与效率二选一 |

**Palantir 的整体设计 = 弥合这三条断裂**，最终交付一个"**可治理的、能行动的、以决策为中心的数字孪生**"。所有子系统都是这句话的分解。

---

## 二、七条第一性原理

每条：**它针对哪条断裂 → 原理 → 体现在哪个子系统**。

### 1. 语义层解耦：Ontology 是一等公民
数据集是"表"，业务是"对象 / 关系 / 动作"。Palantir 坚持在数据之上再建一层**本体（Ontology）**，让人和 AI 都按业务语义（"物料""供应商""这张采购单能不能发货"）工作，而不是按 `t_material.f_qty` 这样的表结构。
→ 针对"数据↔决策"断裂。体现：**[03 Ontology](./03-Ontology本体层.md)**。

### 2. 以决策为中心的数字孪生（Decision-centric Digital Twin）
本体不是为了画一张漂亮的 ER 图，而是为了**支撑决策与行动**——所以对象不仅有属性和链接，还挂着 **Action（可执行、治理化的写回动作）**。本体是"能被操作的世界模型"，不是"数据字典"。
→ 体现：**Ontology Actions（[03](./03-Ontology本体层.md) / [09](./09-AIP-与-Ontology-Actions.md)）**。

### 3. 行动闭环（Kinetic Ontology）
Palantir 的价值不在看板，而在闭环：**读数据 → 人/AI 决策 → 通过治理化 Action 安全写回源系统 → 变更经 CDC 再同步回来**。看板只是闭环的一个观察点。这是 Palantir 区别于"BI + Chatbot"的分水岭。
→ 针对"洞察↔行动"断裂。体现：**Actions 写回 + CDC 回流（[09](./09-AIP-与-Ontology-Actions.md) 与 [SPEC.md](./SPEC.md) 的端到端数据流）**。

### 4. 治理即架构：安全不是功能，是地基
权限被设计成**两层合取（AND）的地基**，任何数据访问必须同时通过：
- **强制层（Mandatory / Markings）**：**否决式**、集中管理、**连资源 Owner 都无法通过"分享"绕过**（官方原文：即使 project owner 试图分享，无资格者也"guaranteed to never be able to access that data"）。
- **自主层（Discretionary / 角色 ACL）**：**只能增加权限，不能收回**（"discretionary controls can only add permissions and cannot restrict"）。

而且**安全"随数据走"（travels with the data）**——给源打的 marking 会**沿血缘自动传播**到所有下游派生数据集，无需在每张下游表重配。
→ 针对"使用↔治理"断裂。体现：**[05 权限与 Markings](./05-权限与Markings.md)、[04 血缘的安全传播](./04-血缘-Lineage.md)**。

### 5. 全程可追溯：血缘 + 审计是底座
- **血缘（Lineage）**：每个数据集从哪来、经哪些 transform、影响哪些下游——**构建时自动登记**，不靠人工维护。
- **审计（Audit）**：每次访问/导出/授权检查/写回——谁、什么、何时、为何（who/what/when/why + traceID），**append-only 不可篡改**（连管理员都无法悄悄抹掉痕迹，删除须走 Palantir 支持的补救流程）。
→ 体现：**[04 血缘](./04-血缘-Lineage.md)、[06 审计](./06-审计-Audit.md)**。

### 6. 数据可信：健康即门禁，不是事后监控
数据质量检查（新鲜度 / schema / 内容 / 期望）被做进**管道构建过程本身**——坏数据在进入下游前就被拦住并告警，而不是等业务发现报表不对再回溯。
→ 体现：**[07 数据健康与监控](./07-数据健康与监控-Data-Health.md)**。

### 7. 操作型 > 展示型
终端交付的是**操作应用（Operational App）**——把数据变成一线员工可以直接点、直接执行动作的任务队列/工作界面，而不是"看完就完"的纯仪表盘。
→ 体现：**[08 Workshop 与管理者视图](./08-应用层-Workshop-与管理者视图.md)**。

## 三、贯穿全局的心智模型（反直觉但关键）

这些是读懂 Palantir 一切文档的"暗知识"，逐条都经官方文档核对：

- **对象 > 表**：一切以对象 / 链接 / 动作组织，表只是"背后的数据集（backing dataset）"。看到"表"要立刻翻译成"这是哪个对象类型的数据源"。

- **权限是 AND 的合取，强制层否决一切**：一个资源贴了 `PII` + `FIN` 两个 marking，用户必须**两个都有资格**才能看——少一个，连这个资源"存在"都看不到（discovery restriction）。这不是"能不能改"，是"能不能看见"。

- **安全跟着数据跑**：marking 有两条继承路径——文件层级级联，以及**数据依赖（data marking）沿血缘传播**。给上游打标，下游自动继承；无资格者能看到派生表的元数据但看不到数据。

- **写权限 ≠ 读权限**：能执行某 Action（写回）与能看到数据是**两条独立的门**。Palantir 甚至支持"改一条你看不到的记录"（Action-only 写回模式，默认只需 Read 权限即可提交对不可见记录的修改）。这对"审批人不该看全量明细却要能批"的企业场景至关重要。

- **目的化授权（PBAC）**：可以把权限授予一个**"目的 / 用途"**而非个人，遵循"**不多不少（no more, no less）**"，申请与授予双方都要记录 rationale，事后可审计"**为什么**这个人当时有权"。

- **审计不可删**：审计链路工程上被设计为 append-only，归档存储访问被"aggressively restricted"；即便要清除数据泄漏痕迹，也须与 Palantir 支持协作走正式补救流程。

- **血缘既是名词也是动词**：它既是"依赖图"（看谁依赖谁），也是"传播通道"——**安全传播、失效标记（out-of-date）、影响分析**都沿血缘走。

- **粒度是组合出来的**：对象安全策略 = 行级；属性安全策略 = 列级；**两者叠加 = 单元格级**。不过对象则整行不可见，过对象但不过属性则该值显示 `null`。

## 四、四大产品的定位（各一句话）

| 产品 | 一句话定位 | 我们的取舍 |
|---|---|---|
| **Foundry** | 数据操作系统：集成 → 转换 → 本体 → 应用 → 治理，一站式 | **主复刻对象** |
| **AIP** | 在本体之上做 LLM 编排与**治理化行动** | 复刻，但**用智能体(agent)实现**（Palantir 偏工作流） |
| **Apollo** | 持续部署与环境治理（拉模式 / 气隙交付） | **愿景**，暂用 GitOps 替代 |
| **Gotham** | 情报 / 调查（政府场景） | **out**（非制造业场景） |

## 五、我们复刻时的"守 · 变 · 简"

- **守（忠实照搬 Palantir 的成熟形式）**：Ontology 语义层；权限两层 AND + 行/列粒度 + 写回权限独立门；审计 append-only + 分类 + trace；血缘 + 安全沿血缘传播；行动闭环；数据健康门禁。**——这些是企业级的"know-how"，正是复刻的核心价值，绝不简化。**
- **变（有意的差异）**：底层引擎用现有栈（StarRocks / Flink CDC / Neo4j / pgvector，而非 Spark / Foundry OSv2）；**AIP 用智能体（agent）实现**；部署用 GitOps（暂不做 Apollo 气隙）。
- **简（PoC 先浅后深，逐层加深）**：多租户自动本体映射、OSDK 全量代码生成、单元格级策略与 CBAC、Apollo 气隙 CD——先搭骨架，按优先级迭代到忠实。
